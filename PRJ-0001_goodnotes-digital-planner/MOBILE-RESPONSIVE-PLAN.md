# PRJ-0001 굿노트 디지털 플래너 모바일 대응 기획서

- 문서 버전: 1.0
- 작성일: 2026-11-21
- 대상 프로젝트: PRJ-0001_goodnotes-digital-planner
- 기준 브랜치: main
- 문서 상태: 기획안
- 범위: 모바일 웹/앱에서 플래너 생성 설정 및 PDF 다운로드, 스마트폰·태블릿에서 PDF 사용성 개선

---

## 1. 기획 목적

기존 굿노트 디지털 플래너 생성기의 핵심 기능(PDF 생성, 연간·월간·주간·일간 페이지, 페이지 간 하이퍼링크, 미리보기 및 상품 문구 생성)을 유지하면서 스마트폰과 태블릿에서도 설정·생성·다운로드할 수 있도록 개선한다.

모바일 대응은 두 영역으로 구분한다.

1. **생성기 UI 모바일 대응**: 스마트폰 브라우저에서 설정을 입력하고 PDF를 생성·다운로드한다.
2. **생성 PDF 모바일 사용성 대응**: 스마트폰에서는 세로형 페이지를 선택할 수 있도록 확장하고, 태블릿에서는 기존 가로형 플래너를 유지한다.

두 영역은 별도 요구사항으로 관리한다. 화면이 반응형으로 바뀌는 것만으로 Python PDF 엔진이 스마트폰에서 실행되는 것은 아니다.

## 2. 현행 구조 및 확인 사항

### 2.1 현행 구성

| 영역 | 현재 구현 | 모바일 관점의 영향 |
|---|---|---|
| UI | React 18, Vite, `ui/src/App.jsx` | 단일 설정 화면이며 모바일 전용 레이아웃·상태 UI가 부족함 |
| 실행 | Electron IPC → Python 엔진 | Electron 데스크톱 앱에 종속되어 일반 모바일 브라우저에서 생성할 수 없음 |
| PDF 엔진 | Python ReportLab | 기존 엔진을 재사용할 수 있으나 서버 또는 모바일 실행 환경 연결이 필요함 |
| PDF 규격 | 842 × 595pt, A4 가로 | 태블릿에 적합한 기본 규격이며 스마트폰 세로 화면에는 축소되어 보일 수 있음 |
| 페이지 탐색 | 우측 연간·월간·노트 탭 및 내부 링크 | 좁은 화면에서 탭 영역과 날짜 링크의 터치 편의성 검증 필요 |
| 결과물 | PDF, PNG 미리보기, listing_copy.json | 모바일 브라우저에서 다운로드·공유 동선이 정의되어 있지 않음 |

### 2.2 현행 코드에서 확인된 제약

- `ui/src/App.jsx`는 연도, 주 시작 요일, 언어, 테마, 주간/일간 포함 여부, 노트 페이지 수를 설정한다.
- 화면은 `maxWidth: 560`의 단일 열 형태이나 입력 요소와 줄바꿈이 반응형 CSS로 설계되어 있지 않다.
- `window.planner`가 있는 Electron 환경에서는 Python 엔진을 호출한다.
- 일반 브라우저에서는 PDF를 만들지 않고 CLI 실행 명령만 화면에 출력한다.
- `desktop/main.js`는 Electron의 IPC 요청을 받아 PC의 Python 실행 파일을 호출한다.
- PDF는 A4 가로(842 × 595pt)로 고정되어 있다.
- README 기준 엔진 테스트 15건은 통과했으나, 실제 굿노트 앱 링크 동작과 한글 폰트 표시, Electron 실행은 별도 확인이 필요하다.

따라서 본 기획은 **반응형 UI 구현과 모바일에서 실제 PDF 생성이 가능한 실행 구조 마련을 함께 진행**하는 것을 전제로 한다.

## 3. 목표 사용자 및 사용 시나리오

### 3.1 사용자 유형

- 스마트폰에서 연도·언어·테마를 선택하고 플래너 PDF를 내려받는 사용자
- 태블릿에서 플래너를 생성하고 Goodnotes 등 PDF 필기 앱으로 가져오는 사용자
- PC에서 상품용 PDF와 미리보기·판매 문구를 생성하는 운영자

### 3.2 핵심 시나리오

1. 사용자가 스마트폰 브라우저에서 생성기 주소에 접속한다.
2. 기본 설정을 확인하고 연도, 요일, 언어, 테마, 페이지 구성을 변경한다.
3. 설정 요약과 예상 페이지 수를 확인한다.
4. 'PDF 만들기'를 누른다.
5. 서버가 기존 Python 엔진을 실행하고 생성 결과 및 링크 검증 결과를 반환한다.
6. 사용자는 생성 완료 화면에서 PDF를 열거나 기기에 저장하고, 미리보기를 확인한다.
7. PDF를 Goodnotes 등 사용 중인 앱으로 가져온다.

## 4. 모바일 대응 범위

### 4.1 1차 범위(MVP)

- React 설정 화면의 반응형 레이아웃
- 모바일 브라우저에서 동작하는 생성 요청 API 연동
- 기존 Python 엔진 재사용
- 생성 진행·성공·실패 상태 표시
- PDF 다운로드 및 미리보기
- 태블릿·PC 화면의 기존 기능 유지
- 입력값 검증 및 서버 측 재검증
- 모바일 Safari 및 Android Chrome 기본 검증

### 4.2 2차 범위

- 스마트폰 세로형 PDF 템플릿
- PDF 내비게이션 탭의 모바일용 배치 개선
- PWA 설치 지원(서비스 워커, 앱 아이콘, 오프라인 캐시 정책)
- 최근 생성 이력 및 재다운로드(사용자 인증·보관 정책 확정 후)
- 상품별 커버·미리보기 프리셋

### 4.3 제외 범위

- Goodnotes 앱 내부 기능을 직접 제어하거나 자동 조작하는 기능
- Etsy·아이디어스·스마트스토어 자동 로그인, 상품 등록 및 결제 처리
- 사용자 동의 없는 PDF 서버 장기 보관
- 1차 단계에서 네이티브 iOS/Android 앱을 별도 개발하는 작업

## 5. 권장 아키텍처

### 5.1 권장안: 반응형 웹 UI + Python 생성 API

기존 React UI와 Python 엔진을 유지하고, 모바일 브라우저와 엔진 사이에 HTTPS API를 둔다.

```
[모바일 Safari / Android Chrome / PC Browser]
                    |
                    v
          [React Responsive UI]
                    |
             HTTPS / JSON
                    |
                    v
             [Python API]
                    |
          [기존 engine 모듈]
                    |
          +---------+----------+
          |         |          |
          v         v          v
       PDF 생성   링크 검증   미리보기 생성
          |         |          |
          +---------+----------+
                    |
                    v
          [PDF / PNG / 결과 JSON]
                    |
                    v
          [브라우저 다운로드·공유]
```

Electron 데스크톱은 기존 방식을 유지한다. 즉, 웹 UI는 API를 호출하고 Electron UI는 기존 `window.planner.generate()` 경로를 사용할 수 있도록 실행 어댑터를 분리한다.

### 5.2 대안 비교

| 대안 | 장점 | 한계 | 판단 |
|---|---|---|---|
| 반응형 웹 + Python API | iOS·Android·PC에서 동일한 UI 사용, 기존 엔진 재사용 | 서버 운영·보안·배포 필요 | **1차 권장** |
| Android WebView APK | 설치형 앱 제공 가능 | Python 엔진 실행·배포 구조를 별도로 해결해야 함 | 후속 검토 |
| 브라우저 내 Python 실행 | 서버 없이 처리할 가능성 | 현재 엔진 의존성·파일 처리·폰트·메모리 검증 필요 | 1차 제외 |
| Electron 화면만 반응형 수정 | PC 창 크기 대응이 쉬움 | 스마트폰에서 Electron 실행 불가 | 모바일 대응으로 불충분 |

## 6. 화면 및 반응형 UX 설계

### 6.1 화면 구성

모바일 화면은 아래 순서의 단일 세로 흐름으로 구성한다.

1. 상단: 서비스명, 현재 단계, 도움말
2. 기본 설정: 연도, 주 시작 요일, 언어
3. 디자인 설정: 테마 선택 카드
4. 페이지 구성: 주간, 일간 포함 여부 및 노트 페이지 수
5. 설정 요약: 선택값 및 예상 페이지 수
6. 하단 고정 영역: PDF 생성 버튼
7. 결과: 생성 상태, 검증 결과, PDF 열기/저장, 미리보기

### 6.2 화면 크기별 레이아웃

| 구분 | 뷰포트 기준 | 레이아웃 |
|---|---:|---|
| 소형 모바일 | 320~359px | 한 열, 좌우 여백 최소화, 테마 2열 |
| 일반 모바일 | 360~767px | 한 열, 터치 입력 중심, 하단 생성 버튼 고정 |
| 태블릿 | 768~1023px | 설정 영역 1~2열, 결과 미리보기 병렬 배치 가능 |
| 데스크톱 | 1024px 이상 | 중앙 최대 폭 컨테이너, 설정과 미리보기 2열 |

브레이크포인트는 초기 설계 기준이며 실제 기기 테스트 결과에 따라 조정한다. 320 CSS px 폭에서도 주요 기능과 텍스트가 잘리거나 가려지지 않아야 한다.

### 6.3 모바일 입력 규칙

- 입력 컨트롤 높이는 기본 44~48px로 설계한다.
- 숫자 입력은 모바일 숫자 키패드를 사용한다.
- 선택 항목은 작은 드롭다운 대신 충분한 터치 영역의 선택 버튼 또는 카드로 제공한다.
- 테마는 색상만으로 구분하지 않고 테마명과 선택 상태를 함께 표시한다.
- 주간/일간 옵션은 터치 가능한 스위치 또는 체크 카드로 제공한다.
- 오류는 해당 입력 바로 아래에 표시하고 오류 문구를 구체적으로 작성한다.
- 생성 중 중복 실행을 막고 진행 상태를 텍스트로 안내한다.
- 화면 하단 고정 버튼이 입력창·키보드·결과 메시지를 가리지 않도록 처리한다.

### 6.4 접근성

- WCAG 2.2 AA의 최소 타깃 크기 기준(24 × 24 CSS px 또는 예외 조건)을 충족하고, 실사용 터치 편의를 위해 주요 버튼은 44 × 44 CSS px 이상을 목표로 한다.
- 키보드 포커스와 스크린 리더용 레이블을 제공한다.
- 텍스트·배경 대비와 오류 상태를 색상 외의 텍스트·아이콘으로도 표현한다.
- 화면 확대 및 세로·가로 회전에 따라 콘텐츠가 유실되지 않도록 한다.

## 7. PDF 모바일 사용성 기획

### 7.1 규격 정책

기존 A4 가로 PDF를 기본값으로 유지한다. 기존 상품 및 링크 구조를 깨뜨리지 않기 위해 스마트폰용 세로형 PDF는 별도 페이지 규격으로 추가한다.

| 프리셋 | 대상 | 방향 | 정책 |
|---|---|---|---|
| Tablet Landscape | 태블릿 필기 | 가로 | 현행 A4 가로 규격 유지 |
| Phone Portrait | 스마트폰 보기·간단 필기 | 세로 | 신규 규격, 별도 레이아웃 설계 후 추가 |
| Print A4 | 인쇄 | 가로/세로 | 기존 규격과 별도 검토 |

Phone Portrait의 정확한 페이지 크기(pt)는 기획 단계에서 고정하지 않는다. 대표 스마트폰의 화면 비율, PDF 뷰어의 표시 방식, 필기 공간을 확인한 뒤 확정한다. 단순히 A4 가로를 축소하는 방식은 사용하지 않는다.

### 7.2 모바일 PDF 레이아웃 원칙

- 날짜·요일·월 이동 기능은 유지하되 터치 가능한 영역을 확보한다.
- 우측 세로 탭은 스마트폰 세로 화면에서 상단 또는 하단 내비게이션으로 재배치하는 방안을 검증한다.
- 주간·일간 페이지의 필기 영역은 화면 폭에 맞게 재배치한다.
- 작은 글씨와 지나치게 촘촘한 날짜 셀을 피한다.
- 기존 PDF 링크 검증 로직을 재사용하되 신규 페이지 규격별 링크 영역 테스트를 추가한다.
- 한글 폰트는 PDF 내장 여부를 확인하고, 폰트 누락 시 생성 완료로 처리하지 않도록 검증한다.

## 9. API 초안

### 9.1 생성 요청

- Method: POST
- Path: `/api/v1/planners`
- Content-Type: `application/json`

요청 예시:

```json
{
  "year": 2027,
  "weekStart": "monday",
  "lang": "ko",
  "theme": "navy",
  "weekly": true,
  "daily": true,
  "notes": 5,
  "pagePreset": "tablet-landscape"
}
```

### 9.2 응답 원칙

생성 시간이 짧은 경우 동기 응답으로 시작할 수 있다. 모바일 네트워크에서 타임아웃이 발생하거나 생성 시간이 길어지는 경우 작업 ID 기반 비동기 처리로 전환한다.

성공 응답에 포함할 항목:
- 작업 상태
- PDF 다운로드 URL 또는 파일 응답
- 링크 검증 성공 여부 및 오류 개수
- 전체 페이지 수
- 미리보기 URL 목록(생성된 경우)

실패 응답에 포함할 항목:
- 안정적인 오류 코드
- 사용자가 이해할 수 있는 오류 메시지
- 재시도 가능 여부

### 9.3 보안 및 파일 처리

- HTTPS만 허용한다.
- 연도·요일·언어·테마·페이지 수 등 입력값을 서버에서 재검증한다.
- 파일명과 저장 경로는 서버에서 생성하며 사용자 입력을 경로에 직접 연결하지 않는다.
- 임시 PDF·PNG는 짧은 보관 기간 후 삭제한다.
- 생성 URL은 추측하기 어려운 임시 토큰 또는 인증으로 보호한다.
- 파일 크기·생성 횟수·요청 빈도 제한을 둔다.
- 서버 로그에 PDF 본문이나 민감한 사용자 입력을 남기지 않는다.

## 10. 데이터·코드 구조 제안

기존 폴더를 최대한 유지하고 실행 경로만 분리한다.

```
PRJ-0001_goodnotes-digital-planner/
├─ engine/                  # 기존 PDF 생성·검증 엔진
├─ ui/
│  └─ src/
│     ├─ components/        # 공통 입력·버튼·상태 UI
│     ├─ features/planner/  # 설정·요약·결과 화면
│     ├─ hooks/             # 생성 상태 및 API 호출
│     ├─ services/          # web/electron 실행 어댑터
│     └─ styles/            # 반응형 토큰·레이아웃
├─ api/                     # 신규 Python API
├─ desktop/                 # 기존 Electron 실행 경로 유지
├─ tests/
│  ├─ api/
│  └─ e2e/
└─ MOBILE-RESPONSIVE-PLAN.md
```

실제 폴더명과 프레임워크는 구현 착수 시 저장소의 기존 의존성과 테스트 환경을 확인하고 확정한다. API 프레임워크는 Python 엔진과의 결합이 단순한 FastAPI를 우선 검토한다.

## 11. 개발 단계 및 완료 기준

### 단계 1. 반응형 UI

- Python 엔진을 호출하는 API 구현
- 서버 입력 검증 및 임시 파일 처리
- UI의 브라우저 실행 경로 연결
- Electron 실행 경로 회귀 확인
- 완료 기준: 모바일 브라우저에서 실제 PDF 생성 및 다운로드 가능

- 임시 파일 정리 및 요청 제한

- 완료 기준: 네트워크 단절·재접속·중복 요청·파일 만료 시나리오 검증

## 12. 테스트 계획

| 구분 | 테스트 항목 | 합격 기준 |
|---|---|---|
| 반응형 | 320~1440px 뷰포트 | 주요 입력·버튼 잘림 및 의도하지 않은 가로 스크롤 없음 |
| 입력 | 연도 2000~2100, 노트 0~50 | 허용 범위·경계값 검증 |
| API | 잘못된 테마·언어·요일·페이지 수 | 4xx 응답, 엔진 실행 전 차단 |
| 생성 | 한국어·영어, 4개 테마 | 기존 엔진 결과와 설정 일치 |
| 링크 | 연간→월간→일간, 탭 이동 | 모든 목적지 존재, 깨진 링크 0건 |
| 파일 | iOS Safari·Android Chrome | PDF 다운로드 및 열기 확인 |
| 폰트 | 한글 제목·요일·본문 | 폰트 누락 없이 정상 표시 |
| 터치 | 탭·버튼·날짜 링크 | 인접 항목 오작동 없이 동작 |
| 회귀 | Electron 데스크톱 | 기존 생성·검증 기능 유지 |
| 네트워크 | 지연·중단·중복 요청 | 중복 생성 방지 및 재시도 안내 |

실제 Goodnotes 앱의 버전·기기별 동작은 자동화 테스트만으로 확정하지 않고 실기기 수동 테스트 결과를 별도로 기록한다.

## 13. 주요 위험 및 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 브라우저에서 Python 엔진 미실행 | UI만 모바일화되고 실제 생성 불가 | 생성 API를 1차 범위에 포함 |
| PDF 생성 시간·메모리 증가 | 모바일 네트워크 타임아웃 | 작업 ID 기반 비동기 처리 전환 기준 마련 |
| 한글 폰트 파일 누락 | 한글 깨짐 또는 대체 폰트 표시 | 배포 패키지에 라이선스와 폰트 포함 여부 검사 |
| 기존 링크 영역 축소 | 터치 오작동 | 페이지 규격별 링크 영역 및 실기기 검증 |
| PDF 임시 파일 노출 | 사용자 결과물 유출 | 임시 토큰, 만료, 저장 경로 분리 |
| 기존 상품과 신규 PDF 호환성 | 구매자 경험 저하 | 기존 A4 가로 프리셋을 기본값으로 유지 |

## 14. 기획 확정이 필요한 항목

아래 항목은 임의로 확정하지 않고 구현 전 결정한다.

1. **모바일 제공 방식**: 모바일 웹 우선(권장) / Android APK 병행 / 네이티브 앱
2. **PDF 규격**: 태블릿 가로형 유지 + 스마트폰 세로형 추가 여부
3. **서버 운영**: 배포 위치, 월 운영비, 생성 파일 보관 기간
4. **인증**: 비회원 임시 생성 / 회원 로그인 및 생성 이력
5. **지원 앱**: Goodnotes 외 PDF 필기 앱 지원 범위
6. **스마트폰 세로형 화면**: 읽기 중심인지, 필기 중심인지

## 15. 최종 권고

1차 목표를 **모바일 반응형 웹에서 기존 플래너 PDF를 실제 생성·다운로드할 수 있게 만드는 것**으로 확정하는 것이 합리적이다.

이때 React UI만 수정해서는 목표를 달성할 수 없다. 현재 브라우저 실행 경로는 CLI 명령 안내만 제공하므로 Python 생성 API가 반드시 필요하다. 기존 A4 가로 PDF는 태블릿용 기본값으로 보존하고, 스마트폰 세로형 PDF는 별도 템플릿으로 2차 개발하는 편이 기존 상품 호환성과 모바일 사용성을 함께 지킬 수 있다.
